### `critique-router-code.json` — router/main.py, router/agents.yaml, router/Dockerfile, router/requirements.txt (OpenAI-compatible routing proxy and agent registry)

The router is a clean 370-line prototype, but it is not a viable OpenAI-compatible surface for coding agents: the Message model accepts only string content and the request model silently drops `tools`, so every tool-using client (Continue agent mode, OpenCode, Open WebUI with tools, Claude Code via proxy) either 422s or degrades to plain chat. It has no fallback when Ollama is down, a 120s whole-stream timeout that will truncate long local generations on a 3060, never sets Ollama `num_ctx` (so the default 2-4k context silently drops the agent persona), and reports no usage, latency, or cost, which makes the owner's "self-developing" requirement impossible because there is no decision log to learn from. The keyword+len//4 classifier is substring-based across the entire conversation (including the client's system prompt and all prior turns), so it both misfires on trivial mentions of "migrate"/"compliance" and becomes sticky once any turn mentions a keyword, while missing short prompts over large contexts. The model IDs (claude-sonnet-4-6, claude-opus-4-8) are stale against the authoritative set, and the six prompts already drift from their Modelfile copies (none are byte-identical, and the router does not even use the Modelfile-built models). Recommendation: retire this router in favour of a LiteLLM proxy (full OpenAI surface, Ollama+Anthropic providers, fallbacks, context-window fallbacks, budgets, spend logging) plus harness-native agent definitions and a small routing hook; keep agents.yaml as the single declarative source that generates everything else.

**Critical / high findings:**
- [CRITICAL] Message.content is str-only and ChatCompletionRequest drops tools: tool-using clients 422 or silently lose tool calling (`router/main.py:61-71`) — Do not hand-roll the OpenAI surface. Put LiteLLM proxy in front of Ollama and Anthropic (it translates content parts, images, tool calls and tool results in both directions). If a custom layer survives, model `content: Union[str, list[ContentPart]]`, add `tools/tool_choice/tool_calls/tool_call_id/name`, and set `model_config = ConfigDict(extra='forbid')` during development so unsupported fields fail loudly instead of silently.
- [HIGH] No fallback or error mapping when Ollama is down; streaming errors surface as a truncated 200 (`router/main.py:188-207`) — Use LiteLLM `fallbacks` + `cooldown_time` for provider failure and `context_window_fallbacks` for the too-long case. If keeping custom code: wrap generator bodies, emit an SSE `error` event or an OpenAI-shaped `{"error":{...}}` chunk before closing, catch the Anthropic typed exception chain most-specific-first (`RateLimitError` -> `APIStatusError` -> `APIConnectionError`), and make `/health` probe `GET {OLLAMA}/api/tags`.
- [HIGH] Ollama `num_ctx` never set: default 2-4k context silently truncates the agent persona (`router/main.py:178-186`) — Always send `options.num_ctx` (per-agent, from agents.yaml) and compute total prompt tokens; if total > local ctx budget, route to cloud (LiteLLM `context_window_fallbacks` does exactly this). Alternatively point `local_model` at the Modelfile-built `agent-*` models so `num_ctx` is baked in, and stop injecting the prompt twice.
- [HIGH] 120s total stream timeout and a new HTTP client per request (`router/main.py:188, 223, 243, 276`) — Use `httpx.Timeout(connect=10, read=60, write=10, pool=10)` so the clock resets on each chunk; create one shared `httpx.AsyncClient` and one `AsyncAnthropic` in a lifespan handler. Set `max_tokens` defaults deliberately rather than relying on client defaults.
- [HIGH] Classifier: substring match over the whole conversation is sticky and misroutes in both directions (`router/main.py:91-108`) — Replace keyword routing with a measurable policy: (a) hard constraints first (total tokens vs local ctx, tool/image presence -> cloud); (b) local-first cascade with self-check: run local, have it emit a machine-readable confidence/escalate token, escalate on low confidence (FrugalGPT-style; this also produces the labelled data a self-developing system needs); (c) later, a learned router (RouteLLM matrix-factorization/BERT router calibrated on your own logs). For known approaches: LiteLLM router handles failure/length fallbacks and budgets but not content difficulty; RouteLLM handles difficulty but needs calibration data; Aider's architect/editor split (Claude plans, qwen edits) fits the 3060 well and is the cheapest reliable split for coding. Whatever is chosen, match whole words with `\b` and classify only the current turn plus a token budget check on the whole context.
- [HIGH] Stale Anthropic model IDs and no cheap cloud tier (`router/agents.yaml:6, 50, 96, 149, 193, 255`) — Make `claude-sonnet-5-5` the default cloud model, `claude-opus-5-5` for security/architecture only, add `claude-haiku-4-5-20251001` as a `cloud_cheap` tier, and define model aliases once (LiteLLM `model_list`) so a model bump is a one-line change. Strip `temperature`/`top_p` before calling Anthropic. Validate configured IDs at startup against `client.models.list()` so the next rename fails fast instead of 404ing at 2 a.m.

**Keep:** agents.yaml as a declarative agent registry (id, description, local/cloud model pairing, context budget): it is the right single source of truth and should generate the Modelfiles, harness agent files and LiteLLM aliases rather than being one of several copies; The local-first, tiered cost idea itself and the per-department pairing of a small local model with a stronger cloud model; only the decision mechanism and the missing mid tier need replacing; Per-agent sampling and num_ctx parameters from the Modelfiles (16k for 14B, 8k for 7B) as explicit configuration, moved into agents.yaml and sent as Ollama options; Compose topology (ollama + proxy + open-webui on one network, agents.yaml mounted read-only) and the non-root, slim Dockerfile pattern; The core persona lines of each prompt (first 3-6 bullets: minimal correct code, test behaviour not implementation, severity-rated findings, 12-factor, keep-a-changelog) which are sound and model-agnostic; The explicit 'escalate' concept in the app-developer prompt, converted from prose into a machine-readable sentinel that a cascade router can act on

### `research-local-models.json` — Best open-weight coding/agentic models for an RTX 3060 12GB (with CPU/RAM MoE offload) as of 2026-10-24, and a 3-tier local lineup for the personal-agent-stack router

Research caveat: from this sandbox, ollama.com, huggingface.co, unsloth.ai and most primary hosts are blocked (proxy CONNECT 403 / DNS fail), so every fact below comes from web-search snippets of primary sources or from secondary write-ups quoting them; exact Ollama tags and sizes are marked medium confidence and must be verified with `ollama pull` on the owner's machine.

The landscape has moved decisively since the repo's current lineup (qwen2.5-coder 7b/14b, deepseek-r1:14b, all dense 2024-25 models). The dominant pattern for 12GB cards in Oct 2026 is a ~30-35B MoE with ~3B active params, run with llama.cpp's expert-offload flag (`--n-cpu-moe N`) so attention/shared weights sit in VRAM and experts sit in system RAM. Measured on an RTX 3060 12GB + 32GB RAM, Qwen3.6-35B-A3B (Apr 2026, Apache-2.0, vendor SWE-bench Verified 73.4) decodes at ~39-47 tok/s with ~9.8GB VRAM and 32k-150k context, i.e. faster than the dense 14B models the repo uses today and roughly 20+ points better on agentic coding benchmarks. Dense 27B models (Qwen3.6-27B 77.2 SWE-V, Qwen3.8-27B) are the best small open coders on paper but do not fit at Q4 (17-18GB) and collapse to ~2 tok/s when offloaded, so they are not viable on this card. No official Qwen3.6/3.8 small (<=9B) or new Qwen3-Coder small release exists; the newest small dense options are Qwen3.5-9B (Mar 2026) and Gemma 4 12B (Jun 2026), both of which fit fully with 32k context but have documented tool-calling flakiness in agent loops.

Critical architectural implication: Ollama still has no expert-aware offload (`--n-cpu-moe` PR #12333 unmerged, issue #11772 open; only layer-granular `num_gpu`), so a 20-24GB MoE on 12GB under Ollama falls back to a slow layer split. The workhorse/reasoning tier should therefore be served by llama.cpp `llama-server` (optionally behind llama-swap) exposing an OpenAI-compatible endpoint, while Ollama remains the convenient host for small models that fit entirely (FIM model, Qwen3.5-9B/Gemma 4 12B fallbacks) and for Open WebUI integration.

Recommended lineup: (1) FIM: `qwen2.5-coder:1.5b-base` on Ollama (~1GB, always resident; Continue's documented default). (2) Workhorse chat+agent: Qwen3.6-35B-A3B UD-Q4_K_XL via llama.cpp (`-ngl 99 --n-cpu-moe 18-26 -fa on -np 1 --cache-type-k q8_0 --cache-type-v q8_0 -c 32768+`), non-thinking mode; fallback if the box has <32GB RAM: `qwen3.5:9b` on Ollama. (3) Local-heavy reasoning/review: the same Qwen3.6-35B-A3B weights with thinking enabled and larger context (zero extra VRAM, no model swap), plus `gpt-oss:20b` at reasoning=high (SWE-bench Verified 60.7, Aider 34.2 per OpenAI card; ~30-50 tok/s partially offloaded on a 3060) as a different-family second reviewer. Stretch: Bonsai 2 27B (Prism ML ternary pack of Qwen3.8-27B, 5.95-7.21GB, Sep 2026; needs PrismML's llama.cpp fork, not Ollama), or Qwen3-Coder-Next 80B-A3B if the host has 64GB RAM. Anthropic cloud tiers should map to the authoritative IDs given in the task (claude-sonnet-5-5 balanced, claude-opus-5-5 heavy, claude-haiku-4-5-20251001 cheap), replacing the stale claude-sonnet-4-6/opus-4-8 strings.

### `research-self-improving.json` — Self-developing mechanisms for a personal local coding-agent stack (Oct 2026): skills, AGENTS.md, memory, trace-driven prompt optimization, eval gates, feedback capture, model promotion

The mature October-2026 pattern for a "self-developing" agent stack is NOT online learning or auto-merge; it is a closed, human-gated loop: (1) capture structured traces and explicit feedback cheaply (Claude Code hooks writing JSONL, Open WebUI thumbs exported via its admin feedback API, router request logs), (2) run a scheduled retrospective in which a model reads the traces and proposes small textual deltas to skills/prompts/routing (ACE-style "delta updates to a playbook", GEPA-style reflection on failing traces), (3) gate every proposal with a deterministic eval harness that includes regression on currently-passing tasks and a comparison against an unchanged control (the Kiro kiro-trace design: 8 PRs opened, 7 merged in week one, with a three-stage preselection/regression/confirmation gate), and (4) deliver the result as a PR a human approves. Two real closed-loop implementations/write-ups with published designs: Kiro's kiro-trace (internal, AWS, 2026) and OpenAI's "Agent Improvement Loop" cookbook (May 2026: traces -> feedback -> Promptfoo evals -> HALO ranking -> Codex handoff, reviewed-PR mode recommended); plus open-source research loops SICA (MIT, agent edits its own code against a benchmark archive) and Karpathy's autoresearch (MIT, program.md + one editable file + 5-minute time-boxed experiments, keep/revert). For the storage format, Claude Code Skills (SKILL.md, open Agent Skills standard, progressive disclosure, hot-reloaded, 500-line guidance) are the right unit of "improvable knowledge", and Anthropic's skill-creator already ships an eval loop (evals.json, with/without-skill runs, grading.json, benchmark with variance, blind comparator, description optimizer) that can serve as the eval gate for skill changes. ### `research-inference-engine.json` — Inference engine and settings for one RTX 3060 12GB on Windows 11 (October 2026): Ollama vs llama-server vs vLLM/LM Studio/Jan/TabbyAPI/SGLang, KV-cache budgets, concurrency behaviour, recommended env vars and model residency

Recommendation: keep Ollama as the single local front door, but run it as the NATIVE Windows app (not the ollama container in infrastructure/docker-compose.yml), because (a) as of v0.40.11 (released 2026-10-24) Ollama serves every GGUF model by spawning the upstream llama.cpp `llama-server` binary, so there is no raw-speed reason to replace it with llama-server for dense models; (b) it already exposes OpenAI-compatible /v1/chat/completions AND an Anthropic-compatible /v1/messages endpoint (Claude Code can be pointed at it with ANTHROPIC_BASE_URL), tool calling, JSON-schema structured output, Modelfile `DRAFT` speculative decoding, and optional Ollama Cloud models; (c) Docker Desktop GPU access on Windows goes through WSL2 passthrough, which adds a VM RAM partition, slower model loads from the Windows filesystem, and the well-known 'GPU disappears after driver update / wsl --shutdown' class of flakiness, with no upside for a single-GPU desktop. The one case where direct llama-server wins is a MoE coder (Qwen3-Coder-30B-A3B, 18.6 GB at Q4_K_M, cannot fit in 12 GB): llama-server's `--n-cpu-moe` keeps attention on the GPU and only expert tensors on the CPU (community reports 17-45 tok/s on 12 GB cards), whereas Ollama only exposes whole-layer offload and no MoE-offload flag. Critical settings on a 12 GB card: Ollama's VRAM-tiered default context is 4096 tokens (<23 GiB VRAM), which is unusable for coding agents and must be raised (OLLAMA_CONTEXT_LENGTH=16384 for a 14B dense model, higher for A3B MoE); set OLLAMA_FLASH_ATTENTION=1 and OLLAMA_KV_CACHE_TYPE=q8_0 (halves KV memory; FA is already 'auto' on supported GPUs but q8_0 requires FA). KV-cache math (q8_0): Qwen3-14B 80 KiB/token -> 1.25 GiB @16k, 2.5 GiB @32k; Qwen3-Coder-30B-A3B 48 KiB/token -> 0.75 GiB @16k, 1.5 GiB @32k, 3 GiB @64k; gpt-oss-20b ~12 KiB/token with SWA-aware cache -> ~0.4 GiB @32k. Fit verdicts for 12 GB (~10.5-11 GiB usable under Windows WDDM): Qwen3-14B Q4_K_M (8.4-9.0 GB) + 16k q8_0 KV fits (about 10.3 GiB total); 32k does not fit without q4_0 KV or a smaller quant. Qwen3-Coder-30B-A3B needs expert CPU offload (needs >=32 GB system RAM) but then 32-64k context is cheap. gpt-oss-20b (MXFP4 ~12-13 GB) spills ~1-2 GB to CPU under Ollama; estimated mid-teens tok/s. Concurrency: with OLLAMA_NUM_PARALLEL=1 (the default) two agents hitting the SAME model are serialized by an in-process semaphore (second waits, no error) and the queue is bounded by OLLAMA_MAX_QUEUE (default 512, then HTTP 503); two agents hitting DIFFERENT 14B-class models cause evict/reload thrash because the scheduler evicts the least-recently-expiring idle runner whenever the predicted footprint exceeds 80% of free VRAM. Therefore on 12 GB only one large model can be resident: pin it with keep_alive=-1, set OLLAMA_MAX_LOADED_MODELS=2 (primary + a <1 GiB embedding or 1.7B helper), and let the router serialize per-model. Important for the current repo: Ollama keys loaded runners by GGUF blob path, so six Modelfile-derived agent models from one FROM share ONE runner (no extra VRAM) as long as their PARAMETERs are identical; an API-time system message overrides the Modelfile SYSTEM, so the duplicated prompts in config/ollama/Modelfile.* and router/agents.yaml can be collapsed to one source of truth (agents.yaml) with a single base model. vLLM and SGLang are poor fits (Linux/WSL2 only, pre-allocated KV pool, partial GGUF support, designed for batch throughput on 24-80 GB cards). TabbyAPI/exllamav3 is VRAM-efficient but has no CPU offload (kills the MoE option) and was slower than llama.cpp on an actual 3060 in the one comparable report. LM Studio 0.4.x (llmster headless daemon, OpenAI API on :1234, CUDA on Windows) and Jan (OpenAI API on :1337, llama.cpp) are viable GUI-first alternatives but add nothing the Ollama + llama-server pair does not already provide.

- (high) Ollama now serves every GGUF model by spawning the upstream llama.cpp `llama-server` binary as a subprocess (its own Go runner is no longer used for GGUF). Consequently Ollama inherits llama-server's auto layer fitting, flash-attention 'auto', KV-cache quantization and speculative decoding, and there is no raw-throughput reason to replace Ollama with a hand-run llama-server for dense models. — https://raw.githubusercontent.com/ollama/ollama/main/llm/server.go
- (high) On a 12 GB card Ollama's default context window is 4096 tokens: the server picks 4096 when total VRAM < 23 GiB, 32768 for 23-47 GiB, 262144 for >=47 GiB, unless OLLAMA_CONTEXT_LENGTH or a per-request/Modelfile num_ctx overrides it. Ollama's own docs say agentic/coding workloads should use at least 64k. - (high) Ollama env-var defaults (source of truth, main branch Oct 2026): OLLAMA_NUM_PARALLEL=1, OLLAMA_MAX_LOADED_MODELS=0 (auto -> 3 per GPU), OLLAMA_MAX_QUEUE=512, OLLAMA_KEEP_ALIVE=5m (negative = infinite, 0 = unload immediately), OLLAMA_KV_CACHE_TYPE=f16, OLLAMA_FLASH_ATTENTION unset (tri-state: unset -> 'auto'), OLLAMA_CONTEXT_LENGTH=0 (VRAM-tiered), OLLAMA_GPU_OVERHEAD=0 bytes, OLLAMA_NO_CLOUD disables cloud features, OLLAMA_REMOTES default 'ollama.com'. — https://raw.githubusercontent.com/ollama/ollama/main/envconfig/config.go

KV-cache quantization (OLLAMA_KV_CACHE_TYPE=q8_0/q4_0) is passed as `--cache-type-k/--cache-type-v`, applies globally to all models, and per Ollama's FAQ only takes effect with flash attention; q8_0 ~ half of f16 with negligible quality loss, q4_0 ~ quarter with small-to-medium loss that grows with context and with high-GQA models. — https://github.com/ollama/ollama/blob/main/docs/faq.mdx
- (high) Same-model concurrency: Ollama launches llama-server with `-c num_ctx*num_parallel -np num_parallel` and wraps it in an in-process weighted semaphore of size num_parallel. With the default NUM_PARALLEL=1, a second simultaneous request to the same model blocks on the semaphore until the first completes (no error, honours client cancellation); setting NUM_PARALLEL=2 doubles the KV allocation (each slot gets a full num_ctx) in exchange for batched decoding. Overflow beyond OLLAMA_MAX_QUEUE pending requests returns HTTP 503 'server busy, please try again. maximum pending requests exceeded'. — https://raw.githubusercontent.com/ollama/ollama/main/llm/llama_server.go
- (high) Different-model concurrency: when a request arrives for a model that is not loaded, the scheduler predicts its VRAM (weights + KV for num_ctx*num_parallel + batch buffers); if the prediction exceeds 80% of currently free memory it evicts another runner, choosing an idle one (refCount==0) sorted by soonest expiry/name, and if none is idle it waits for the in-flight request to finish and then unloads. On a 12 GB card this means two agents using two different ~9 GB models alternately will reload each switch (seconds each) rather than run together; only pairs whose combined footprint fits (e.g., a 14B Q4 + a <1 GiB embedding model) are co-resident. — https://raw.githubusercontent.com/ollama/ollama/main/server/sched.go
- (high) Ollama keys loaded runners by the GGUF blob path (ModelPath), not by model name. ### `research-mcp-tools.json` — MCP and tool ecosystem for department coding agents (October 2026): spec/registry status, essential servers, security, orchestrator-as-MCP-server pattern, Open WebUI/A2A, and per-client config formats

The MCP ecosystem in October 2026 is stable enough to build on but has just gone through its largest break: spec revision 2026-07-28 removed sessions and the initialize handshake, made Mcp-Method/Mcp-Name headers mandatory on Streamable HTTP POSTs, deprecated Roots/Sampling/Logging and the old HTTP+SSE transport (12-month windows), deprecated OAuth DCR in favour of Client ID Metadata Documents, and moved long-running Tasks into an extension (io.modelcontextprotocol/tasks, poll-based). All Tier-1 SDKs speak it (python `mcp` 2.3.0, `fastmcp` 4.1.3, TS SDK 1.32.2 as of Oct 2026). The official registry is still a preview (API v0.1 frozen, ~30-45k entries) and verifies only namespace ownership, not code safety, so it must not be treated as a trust signal.

The reference-server set has shrunk: only everything/fetch/filesystem/git/memory/sequential-thinking/time remain (filesystem/memory/sequential-thinking 2.0.0 need Node 24); GitHub, Postgres, SQLite, Puppeteer etc. are archived. The practical coding toolset is: filesystem (allowed dirs by CLI args; read-only only via Docker `,ro` mounts), mcp-server-git, GitHub's official server (remote at api.githubcopilot.com/mcp or local Docker, with `--toolsets` and `--read-only`), Playwright MCP (`@playwright/mcp`, `--headless --isolated`, `--port` gives Streamable HTTP), Context7 (remote `https://mcp.context7.com/mcp`, tools resolve-library-id/query-docs), Serena 2.1.0 (LSP symbol tools, `--context claude-code`, modes planning/editing, `--transport streamable-http --port`, one instance per project), Semgrep MCP (beta) and Aqua's Trivy MCP plugin for security.

Client config formats are settled: Claude Code uses `.mcp.json` (`mcpServers`, `type: stdio|http`, `${VAR}` expansion, tool search deferral on by default, per-server `timeout`, `alwaysLoad`) plus `.claude/agents/*.md` whose `mcpServers:` and `tools: mcp__server__*` fields scope servers per subagent; OpenCode uses `opencode.json` with an `mcp` map (`type: local|remote`, `command` array, `environment`, `url`, `headers`, `timeout` default 30 s) and `tools: {"server_*": false}` per agent; Continue uses `.continue/mcpServers/*.yaml` (`type: stdio|sse|streamable-http`, agent mode only); Open WebUI (>=0.6.31) is natively Streamable-HTTP-only (Admin > Integrations > External Tool Servers, needs WEBUI_SECRET_KEY) and otherwise needs mcpo (last release Feb 2026, slow maintenance). Because MCP calls are synchronous and client timeouts are short (OpenCode 30 s), delegate must return a job handle for long work (the 2026-07-28 guidance literally says to mint handles and pass them back as arguments).

Security: OWASP MCP Top 10 (MCP03 tool poisoning, MCP06 prompt injection via context, MCP02 scope creep) and the Client-Side Tool Risk Gating control give the concrete playbook: pin every tool definition by SHA-256 on first sight and quarantine silently changed tools (rug-pull defence), classify tools from `readOnlyHint/destructiveHint` annotations, require human approval for destructive tools, deny by default above a ceiling, and never auto-approve. Claude Code supports this natively via per-tool permission rules, `.mcp.json` project approval prompts, and the `_meta["anthropic/requiresUserInteraction"]` flag; MCP has no built-in signed manifests, so pin package versions (no `@latest`) and ship a fingerprint file. A2A reached v1.0.0 (Mar 2026) / v1.0.1 (May 2026) under the Linux Foundation but is irrelevant for a single-user stack; MCP delegation covers the need. The repo's Continue config still names `claude-sonnet-4-6`/`claude-opus-4-8`, which must be replaced with the authoritative IDs.
